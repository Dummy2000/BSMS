H1   Live recording finds no beats for the first ~55 s
     HIGH | DSP | VERIFIED
------------------------------------------------------------------------------------------
Where:    bsms_app/lib/data/ble/ble_recording_service.dart, class _StreamingPipeline
          - filter state starts at 0 (L302-304), processSample (L360-392)
          - 2 s threshold learning in _detect (L396-405)
What:     The live detector's filters start from zero. The first raw sample (~13200 LSB,
          the ADS1115 baseline) is a huge step for the 0.5 Hz high-pass. The transient
          dominates the 2 s learning window, so SPKI/NPKI start far too high and then
          decay at only ~5.75 %/s.
Impact:   Roughly the first minute of every BLE recording has (almost) no R-peaks, so
          HR, HRV and events are missing there. The transient also produces fake peaks
          at the very start (through the H2 searchback bug).
Evidence: 10 min synthetic ECG at 75 bpm, raw values including the baseline:
          - 8 fake peaks at samples 75-82
          - first real beat found at 54.8 s
          - minute 1: 7 of 73 beats found, plus 39 fake/duplicate peaks
          - minutes 2-10: 75 of 75 each
          Same signal with the baseline subtracted: every beat found.
          The firmware is not affected: it subtracts the boot baseline first
          (main.cpp L525).
Fix:      Pre-warm the filter state with the first sample (EcgFilter.bandpass already
          does this) or subtract a baseline before filtering. Seed the thresholds
          robustly (skip the first ~0.5 s, or use the median of per-second maxima
          instead of the maximum).
Status:   FIXED 2026-11-18. The high-pass state now starts from the first sample, so
          the baseline causes no step. In addition: if no beat has been found 3 s
          after learning and the last 2 s stay below half of the learned level, the
          thresholds are learned again (an artefact in the first 2 s now costs ~5 s
          instead of ~38 s), and searchback only runs after a first beat.
          Test: bsms_app/test/streaming_pipeline_test.dart

H2   Searchback stores duplicate R-peaks
     HIGH | DSP/FW | VERIFIED
------------------------------------------------------------------------------------------
Where:    bsms_app/lib/data/ble/ble_recording_service.dart _StreamingPipeline._searchback
          (L511-534, loop at L519)
          ESP32code/src/main.cpp detectPeakPT, searchback block (L246-271, loop at L256)
What:     When no beat was found for 1.66 x mean RR, the code takes the largest MWI
          value from the buffer. The intent is to skip the 200 ms right after the last
          beat. The loop instead skips the newest 200 ms ("k" counts back from now) and
          runs right up to the sample after the last beat. The maximum is then usually
          at a window edge: the falling tail of the previous beat, or the rising edge of
          the current one. After a hit, the same thing happens again a few samples later.
Impact:   Fake R-peaks 1 sample apart, or one beat stored twice ~100 samples apart. They
          are written to the R-peak file and end up in the CSV export, HRV and event
          detection. Each one also becomes the "last beat" reference (the next RR is
          measured from it) and lowers SPKI. The session viewer only hides them
          (minGap = 100, imported_session_screen.dart L182). In the firmware, RRs below
          250 ms don't change the HR, but the reference and SPKI are still affected.
Evidence: Synthetic ECG, baseline removed, 35 beats with a 3 s pause after the beat at
          sample 9800 -> 39 stored peaks:
          - the first beat (sample 1000) is stored twice: 986 and 1086
          - 9892, 9893 and 9894 inside the pause (the real beat was detected at 9835)
          In the H1 run: 31 duplicates 1 sample apart around 55-56.5 s.
Fix:      Search only from (last beat + 200 ms) to (now - a small margin), i.e. k from
          ~0 to samplesSinceBeat - 100. Accept only a real local maximum, not a window
          edge. Never store a peak closer than 200 ms to the previous one. Apply the
          same fix in main.cpp.
Status:   FIXED 2026-11-18 in the app and in main.cpp. Window = from 200 ms after the
          last beat to 200 ms before now, only real local maxima. In addition:
          candidates within 360 ms of the last beat must pass the T-wave check, and
          searchback doesn't run while a peak is being tracked. Recordings made
          before the fix keep their stored duplicates.
          Test: bsms_app/test/streaming_pipeline_test.dart (app). The firmware was
          compiled and checked with a Dart port of detectPeakPT, not on hardware.

H3   One unusual early RR interval blocks all HRV values
     HIGH | DSP | VERIFIED
------------------------------------------------------------------------------------------
Where:    bsms_app/lib/domain/processing/hrv_calculator.dart _acceptRr (L91-98), used by
          nnIntervals (L101-111) and the live addPeak (L64-86)
What:     An RR interval is kept only if it differs by at most 20 % from the previous
          *accepted* interval. If that reference is unusual (a missed beat or artefact
          at the start, or HR changed during a lead-off or BLE gap), every later normal
          interval differs by more than 20 % and is rejected. The reference never moves
          again.
          Also: RMSSD uses differences between consecutive *kept* intervals, even when
          rejected intervals lay between them. Only originally adjacent pairs should be
          used.
Impact:   SDNN, RMSSD and live RMSSD can stay empty for a whole recording.
Evidence: R-peaks at 0, 1500, 2300 ms and then every 800 ms (1 x 1500 ms + 101 x 800
          ms): nnIntervals keeps 1 interval ([1500]); SDNN = null, RMSSD = null, live
          RMSSD = null.
Fix:      Compare against a robust reference (median of the last 5-10 raw RRs), or
          reset the reference after a few consecutive rejections. Compute successive
          differences only for originally adjacent intervals. Add this case as a test.
Status:   FIXED 2026-11-18. The reference is the median of up to 3 plausible
          intervals on each side (live: the last 6), and RMSSD only pairs intervals
          that were adjacent before filtering.
          Test: bsms_app/test/hrv_calculator_test.dart

H4   Offline detector: early artefact blinds it for ~50 s
     HIGH | DSP | VERIFIED
------------------------------------------------------------------------------------------
Where:    bsms_app/lib/domain/processing/r_peak_detector.dart _panTompkins
          - seed = maximum of the first 2 s (L59-62)
          - decay only if meanRr > 0, and only for SPKI (L73-76)
          Used for SD imports (viewer) and SD CSV export.
What:     Thresholds are seeded from the largest MWI value in the first 2 s, so one
          artefact there (movement, touching an electrode, an ADC step) makes SPKI many
          times too high. The recovery decay only runs after two accepted peaks
          (meanRr > 0), lowers only SPKI and is slow (~5.75 %/s). The live and firmware
          detectors decay both thresholds and use a default gap when RR is unknown;
          their comments explain why SPKI alone isn't enough.
Impact:   Beats are missing for a long stretch, which gives false pauses/bradycardia and
          wrong mean HR and HRV. If the artefact yields no accepted peaks at all, the
          decay never starts (from reading the code; not simulated).
Evidence: 60 s synthetic ECG at 75 bpm. Clean: 75 of 75 found. With a 300 ms,
          +8000 LSB step at t = 1 s: 17 peaks, of which 15 are real beats; nothing
          between 1.5 s and 49.5 s.
Fix:      Seed from a robust value over a longer window (e.g. median of per-second
          maxima over 8-10 s), use the same decay as the live detector, and re-learn
          after N seconds without a beat.

H5   BLE disconnect also stops SD logging (uncommitted change)
     HIGH | FW/BLE | READ
------------------------------------------------------------------------------------------
Where:    ESP32code/src/main.cpp (uncommitted):
          - MyServerCallbacks::onDisconnect sets g_active = false (L372-378)
          - loop() returns early in standby (L514-517)
          - start/standby commands (L349-361)
          bsms_app/lib/data/ble/ecg_ble_service.dart: a disconnect is only reported
          (L132-137); there is no reconnect.
What:     On every BLE disconnect the ESP switches to standby and stops sampling,
          including SD logging. After a reconnect it waits for a new start command, and
          the app does not reconnect by itself. SD logging also only runs after the app
          has started a measurement, so the ESP can't record on its own.
Impact:   Phone out of range, a BLE glitch or the app being killed (see M26) ends the
          recording on the phone AND on the SD card. The SD card can no longer bridge
          BLE dropouts, which is the main reason a Holter has one.
Fix:      Decide before committing. Proposal: keep sampling and SD logging independent
          of the link (a disconnect only stops notifications; standby only via the
          explicit 0x00 command or a button). Add auto-reconnect in the app that resumes
          the running recording. Optionally add a "measuring" bit to status_flags so the
          app can see the device state.

H6   SD import loads everything into RAM on the UI thread
     HIGH | IMPORT | READ
------------------------------------------------------------------------------------------
Where:    bsms_app/lib/data/import/sd_card_import_service.dart
          - importFromFile: withData: true (L14-18)
          - parseBytes: one EcgSample object per sample (L107-115)
          bsms_app/lib/presentation/history/imported_session_screen.dart initState:
          EcgFilter.bandpass + RPeakDetector.detect (L95-96)
What:     The whole file is read into memory and turned into one Dart object per
          sample. The viewer then builds a second, filtered list and runs detection.
          All of this happens on the UI isolate.
Impact:   12 h = 21.6 million samples. Rough estimate: 0.4-0.9 GB for the parsed list
          and about the same again for the filtered copy. Long recordings freeze the app
          for a long time or get it killed (out of memory).
Fix:      Stream-parse in a background isolate and convert the file into the
          file-backed format BLE recordings already use (51-byte blocks + R-peak file +
          HR file), then open it in the existing file-backed viewer. Also solves M22.

H7   SD import counts ~39 "skipped" packets per packet
     HIGH | IMPORT | READ
------------------------------------------------------------------------------------------
Where:    bsms_app/lib/data/import/sd_card_import_service.dart parseBytes (L70-75)
What:     Gap detection reads bytes 0-3 as a packet counter. In the 51-byte format these
          are the low 32 bits of the millisecond timestamp, which grows by 40 per packet,
          so each packet adds 39 "missing" packets.
Impact:   skippedPackets is ~39 x the packet count (~42 million for 12 h). The import
          snack bar shows this number (history_screen.dart L69-73). Real gaps can't be
          told apart.
Fix:      For 51-byte files use the uint64 timestamps: a gap is a delta > 40 ms plus
          tolerance, and missing = round(delta / 40) - 1. Keep the counter logic for
          47-byte files.

H8   Clock hard-coded to UTC+2; SD imports have no time
     HIGH | UI | READ
------------------------------------------------------------------------------------------
Where:    bsms_app/lib/presentation/live_ecg/live_ecg_screen.dart L280 (utcOffsetMs)
          bsms_app/lib/presentation/history/imported_session_screen.dart L283-291
          (_utcOffsetMs, _formatAsViennaTime), used by _formatWindowPosition (L293) and
          _eventTimeFmt (L307)
          ESP32code/src/main.cpp L27-28 (UTC_OFFSET_HOURS, serial output only)
What:     Wall-clock time is computed as UTC + 2 h. Since the switch to CET at the end
          of October, every displayed time is 1 h ahead in Austria, and it is wrong in
          any other time zone. SD imports have no absolute time at all (sample index x
          2 ms, starting at 0), so their time axis starts at a made-up "2:00:00".
Fix:      Format via DateTime.fromMillisecondsSinceEpoch(ms) (device time zone incl.
          DST) and intl DateFormat. For SD imports use the packet timestamps (H7, M15).
          Firmware: keep UTC on the wire and on SD; for serial output use a POSIX TZ
          rule such as "CET-1CEST,M3.5.0,M10.5.0/3".

M1   BLE recordings mix sample-index time and device time
     MEDIUM | BLE | READ
------------------------------------------------------------------------------------------
Where:    bsms_app/lib/data/ble/ble_recording_service.dart _onPacket (L194-261):
          R-peaks and HRV use sample index x 2 ms (L229-235); lead-off intervals
          (L240-249) and the HR file (L218-225) use device timestamps.
          bsms_app/lib/presentation/history/imported_session_screen.dart: HR and events
          from peak indices plus applyLeadOff (L83-89); clock = index x 2 + first
          timestamp (L293-308).
What:     The stored waveform has no gaps (packets are simply appended), so everything
          index-based lines up: waveform, R-peak markers, events and event navigation.
          Lead-off intervals and the HR file use device time, which keeps running during
          a BLE gap.
Impact:   After a gap of G seconds:
          - lead-off shading is drawn G s too late and applyLeadOff removes the wrong
            events
          - displayed clock times fall behind by the sum of all earlier gaps
          - the RR interval across the gap ignores the missing time, giving one false HR
            value and possibly a false event
          - the live detector treats both sides of the gap as continuous signal
Fix:      Use one time base. Simplest: keep the sample index, convert lead-off to
          indices while recording, store each gap as (index, real duration from the
          device timestamps), add the gap durations when showing clock times, and don't
          compute RR across a gap.

M3   R-peak markers sit ~85 ms after the R apex
     MEDIUM | DSP | VERIFIED
------------------------------------------------------------------------------------------
Where:    bsms_app/lib/data/ble/ble_recording_service.dart _detect (the peak is the MWI
          maximum, L449-472); the same in r_peak_detector.dart (L101) and the firmware
What:     The stored index is the maximum of the 150 ms moving-window integral, which
          lags the R apex. RR intervals are fine because the lag is almost constant, but
          the markers and the CSV column is_r_peak are off.
Evidence: Lag: median 42 samples (84 ms), maximum 48 (96 ms). Peaks found by searchback
          can be ~20-30 ms early.
Fix:      After detection, refine the position: take the maximum of |bandpassed signal|
          within ~150 ms before the MWI peak and store that index.

M4   Detector bands don't fit Pan-Tompkins; 2 HR sources
     MEDIUM | DSP/FW | CALCULATED
------------------------------------------------------------------------------------------
Where:    bsms_app/lib/data/ble/ble_recording_service.dart _computeCoefficients
          (L537-556: HP 0.5 Hz, LP 40 Hz, notch 50 Hz)
          bsms_app/lib/domain/processing/r_peak_detector.dart (gets EcgFilter output,
          0.5-40 Hz)
          ESP32code/src/main.cpp bandpass biquad (L116-118)
          bsms_app/lib/presentation/live_ecg/live_ecg_screen.dart L454
What:     Pan-Tompkins expects ~5-15 Hz before the derivative, to suppress P/T waves and
          baseline wander. The app detectors get 0.5-40 Hz, so there is more T-wave and
          noise energy in the MWI.
          The firmware biquad (b = 0.0305, 0, -0.0305; a = -1.9347, 0.9389) peaks at
          5.2 Hz with a -3 dB band of 3.3-8.3 Hz. Relative to the peak, 10 Hz is at
          -4.9 dB and 15 Hz at -9.0 dB: too low for the QRS energy.
          Two HR sources: the live screen shows the firmware HR, but the app pipeline's
          HR while recording (L454), so the value can jump when a recording starts. The
          two also handle outliers differently (see L10).
Fix:      Use a dedicated 5-15 Hz bandpass for detection and keep 0.5-40 Hz for display.
          Redesign the firmware biquad for 5-15 Hz at 500 Hz. Choose one HR source.

M8   Packet reassembly can lose framing until reconnect
     MEDIUM | BLE | READ
------------------------------------------------------------------------------------------
Where:    bsms_app/lib/data/ble/ecg_ble_service.dart _subscribeToNotifications (L159-181)
What:     Notifications are appended to a byte buffer and cut into 51-byte pieces. BLE
          never splits one notification (a too-small MTU truncates it instead), so this
          only adds risk. One notification of a different length shifts every following
          packet. Most then fail to parse (sample_count != 20) and the rest are garbage,
          until the next reconnect.
Fix:      One notification = one packet: parse it if its length is 51, otherwise drop
          and count it.

     MEDIUM | BLE | READ

Fix:      Drop deinitialize(), fix or remove BleDeviceConnector, emit false in stop(),
          and scan with withServices: [serviceUuid] and a timeout with a message.

     MEDIUM | BLE | READ

     MEDIUM | FW | READ
------------------------------------------------------------------------------------------
Where:    ESP32code/src/main.cpp: deviceConnected (L41, not volatile); the time sync

VERIFICATION RECIPES (synthetic ECG - can be turned into unit tests)
==========================================================================================
Signal: 500 Hz, integer samples. Baseline 13200 LSB plus uniform noise of +-10 LSB.
  Each beat: R = Gaussian of +1000 LSB, sigma 10 samples (20 ms);
             T = Gaussian of +250 LSB, sigma 20 samples, 125 samples (250 ms) after R.
  RR = 400 samples (800 ms, 75 bpm) unless stated otherwise.
Exact counts depend on the random noise (Dart Random seeds 1, 3 and 2 were used for H2,
H1 and H4); the pattern does not.

H1  Live pipeline, raw input: beats every 400 samples from sample 1000 for 10 min (748
    beats). Feed the raw values (with baseline) sample by sample into StreamingPipeline.
    Expected: nearly all beats, and no peaks before the first beat.
    Before:   8 peaks at samples 75-82; first real beat found at 54.8 s; minute 1: 7 of
              73 found plus 39 fake; then 75 of 75 per minute.
    After:    748 of 748 found, no fake peaks, first peak at sample 1044 (2026-11-18).
H2  Live pipeline, baseline subtracted: beats at 1000, 1400, ..., 9800, then a 3 s
    pause, then 11300, 11700, ... up to 16000 (35 beats).
    Expected: 35 peaks, none closer than 100 samples.
    Before:   39 peaks; the extras are 1086, 9892, 9893 and 9894; the smallest gap is
              1 sample.
    After:    35 peaks, no extras, smallest gap 390 samples (2026-11-18).
M3  Same run: detection index minus true R is median 42, max 48 samples (84 / 96 ms).
H3  HrvCalculator.nnIntervals([0, 1500, 2300, 3100, ... every 800 ms, 100 more]).
    Expected: ~101 NN intervals.
    Before:   1 ([1500]); SDNN, RMSSD and live RMSSD are all null.
    After:    101 (all 800 ms); SDNN, RMSSD and live RMSSD are 0 (2026-11-18).
H4  60 s, beats every 400 samples from sample 300 (75 beats), plus +8000 LSB on samples
    500-649; then EcgFilter.bandpass -> RPeakDetector.detect.
    Expected: ~75.
    Now:      17 peaks (15 real), none between 1.5 s and 49.5 s. Without the artefact:
              75 of 75.
M4  Firmware biquad: evaluate H(z) = (0.0305 - 0.0305 z^-2) / (1 - 1.9347 z^-1 +
    0.9389 z^-2) at fs = 500 Hz: peak at 5.2 Hz, -3 dB at 3.3 and 8.3 Hz.

The numbers above come from throwaway Dart scripts that call the real classes. The
H1-H3 cases are now unit tests: bsms_app/test/streaming_pipeline_test.dart and
bsms_app/test/hrv_calculator_test.dart.
